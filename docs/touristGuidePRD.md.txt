1. Core Functionality
1.1 User Management (Better Auth)
Registration: Email/password + OAuth (Google, Facebook) via Better Auth

Authentication: Better Auth handles sessions, JWT, refresh tokens, email verification

Roles: admin, tour_guide, tourist (stored in User table)

Profile: Name, email, phone, address, profile image, date of birth

1.2 Package Management
CRUD Operations: Create, read, update, delete tour packages (admin only)

Properties: title, description, price, duration, tourType, location, images, tourPlan (JSON)

Search & Filter: By title, tourType, location, price range with pagination

1.3 Booking System
Create Booking: Tourist creates a booking request for a package

Properties: tourDate, totalPrice, discountApplied, status (in_review/accepted/rejected/cancelled/paid)

Flow: Tourist books → Tour guide accepts/rejects → Tourist pays (Stripe)

1.4 Wishlist & Stories & Reviews
Wishlist: Tourists add packages to wishlist (unique per user-package)

Story Sharing: Tourists share travel stories with images (max 5), likes

Reviews: Tourists rate tour guides after trip completion

1.5 Payment System
Stripe Integration: Payment intent creation, webhook handling

Discount Logic: User books ≥3 paid trips → 10% discount on next booking

PDF Invoice: Generated via PDFKit, uploaded to Cloudinary, emailed

1.6 Admin Features
Dashboard stats, user management (search, filter by role, role change), offer management, bulk package import

1.7 Tour Guide Features
Profile (specialization, qualification, experience, fee, availability), assigned tours, earnings tracking

1.8 Notification System
Email (Nodemailer) + in-app notifications (Notification table)

2. Product Data Model (PRD Style)
Better Auth provides its own tables: user, session, account, verification. We extend the user table with custom fields.

1️⃣ User (extended with custom fields)
Description
A user represents any person using the platform. Roles: Admin, Tour Guide, Tourist.

Attributes (Better Auth default + custom)

ID (cuid)

Email (unique)

Email verified (boolean)

Name

Image (profile picture)

Phone (optional)

Role (ADMIN / TOUR_GUIDE / TOURIST, default TOURIST)

Address (optional)

Date of birth (optional)

isRequestedTourGuide (boolean, default false)

Deleted at (soft delete)

Created at, updated at

Relationships

A user can create multiple bookings (if tourist)

A user can create multiple stories (if tourist)

A user can create multiple reviews (if tourist)

A user (if tour guide) has one TourGuideProfile

A user can add multiple wishlist items

A user has multiple notifications

2️⃣ TourPackage
Description
A tour package represents a travel plan offered on the platform.

Attributes

ID (uuid)

Title

Slug (unique)

Description (text)

Price (float)

Duration (days)

Tour type (string)

Location

Images (string array)

Overview (text, optional)

Tour plan (JSON array)

isActive (boolean)

Created at, updated at, deleted at (soft delete)

Relationships

A package can have multiple bookings

A package can be added to multiple wishlists

3️⃣ Booking
Description
A booking represents a tour package reservation created by a tourist.

Attributes

ID (uuid)

Status (IN_REVIEW, ACCEPTED, REJECTED, CANCELLED, PAID)

Tour date (DateTime)

Total price (float)

Discount applied (float, default 0)

Payment intent ID (string, optional)

Created at, updated at, deleted at

Relationships

Belongs to one user (tourist)

Belongs to one tour package

Can be assigned to one tour guide (after acceptance)

Has one payment record

4️⃣ TourGuideProfile
Description
Additional profile for users with role TOUR_GUIDE.

Attributes

ID (uuid)

Specialization (string)

Qualification (string)

Experience (int)

Fee (float, optional)

Available days (string array)

Available time slot (string)

Bio (text, optional)

Certificate URL (string, optional)

Contact email, contact phone (optional)

Earnings total (float, default 0)

Created at, updated at

Relationships

Belongs to one user

Can have multiple assigned bookings

Can receive multiple reviews

5️⃣ Wishlist
Attributes: ID, userId, packageId, createdAt
Constraint: unique userId+packageId

6️⃣ Story
Attributes: ID, userId, title, content, images (array, max 5), location, likes, createdAt, updatedAt

7️⃣ Review
Attributes: ID, userId, guideId, rating (1-5), comment, createdAt

8️⃣ Payment
Attributes: ID, bookingId (unique), amount, stripePaymentIntentId, status, receiptUrl, createdAt

9️⃣ Offer
Attributes: ID, title, description, discountCode, validUntil, isActive, createdAt

🔟 Notification
Attributes: ID, userId, title, message, type, isRead, createdAt

🔗 Relationship Summary
User → many Bookings, Stories, Reviews, Wishlist items, Notifications

User (Tour Guide) → one TourGuideProfile

TourGuideProfile → many Reviews, many Bookings (as guide)

TourPackage → many Bookings, many Wishlist items

Booking → one User, one TourPackage, one Payment, one TourGuideProfile (optional)

🧠 Business Rules
Only users with role TOUR_GUIDE can accept/reject bookings

Only one bid (acceptance) per booking

When a booking is accepted, status becomes ACCEPTED; tourist can then pay

When payment succeeds, status becomes PAID

Reviews only after trip completion (PAID and tourDate passed)

Wishlist unique per user-package

Discount: 3+ PAID bookings → 10% discount on next booking

Request to become guide: Tourist requests → admin approves → role changes to TOUR_GUIDE, empty profile created

Search & Filter: packages by title/location (contains), tourType exact, price range

Pagination: page, limit (default 10, max 100)

Soft delete: User, Package, Booking (deletedAt)

Auto-cancel IN_REVIEW bookings older than 48 hours (cron)

Reminder email 24 hours before tour date (cron)

6. Business Logic Rules (Detailed)
Registration: Better Auth handles hashing, email verification. Default role = TOURIST.

Login: Better Auth creates session. Session contains user role.

Auth Middleware: Wrapper around Better Auth's getSession to attach req.user.

Role Middleware: Checks req.user.role.

Create Booking: Tourist must be authenticated; package exists; tourDate future.

Accept/Reject: Only guide assigned to booking can change status. On accept → status ACCEPTED, on reject → REJECTED.

Payment Flow: After acceptance, tourist creates Stripe payment intent; webhook sets status PAID.

Discount Rule: Count PAID bookings for user; if ≥3, allow 10% discount on next booking.

Wishlist: Unique constraint on userId+packageId.

Review: Only allowed if user has PAID booking with that guide and tourDate passed.

Request to become guide: Set isRequestedTourGuide=true; admin approves → role changes, TourGuideProfile created.

Search & Filter: Prisma contains (case-insensitive) for title/location; exact match for tourType; gte/lte for price.

Pagination: All GET lists support page, limit (default 10, max 100), sortBy, sortOrder.

Soft delete: deletedAt field; excluded from queries by default.

Cron Jobs:

Hourly: cancel IN_REVIEW bookings older than 48 hours.

Daily 8 AM: send reminder email for next day's tours.

8. Deployment Checklist
Set NODE_ENV=production

Configure PostgreSQL (Neon/Supabase)

Set all environment variables

Run npx prisma generate && npx prisma migrate deploy

Run seed script to create admin user (using Better Auth API or direct insert)

Build: npm run build

Start: npm start

Configure Stripe webhook to https://yourdomain.com/api/v1/payments/webhook
